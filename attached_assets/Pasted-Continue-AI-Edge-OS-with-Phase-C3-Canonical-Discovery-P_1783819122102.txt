Primary objective

Implement the production-ready persistence layer for the canonical discovery engine using the existing Drizzle/PostgreSQL architecture while preserving all Phase C2 behavior, determinism, tenant isolation, fault tolerance, and provider independence.

Start with an audit-first workflow. Before writing code:

1. Read the Phase C1 architecture document.
2. Read all Phase C2 discovery modules and tests.
3. Audit the existing Drizzle schema, migrations, repositories, database helpers, transaction patterns, tenant-scoping conventions, test database setup, and generated types.
4. Search for any existing discovery, opportunity, signal, cluster, analytics, research, trend, or content-idea persistence structures that should be reused or extended.
5. Identify redundant or overlapping tables, types, repositories, and APIs.
6. Produce a concise implementation plan and proposed file changes before editing code.

Do not assume a migration is necessary. First determine whether existing schema can support the required persistence model cleanly. If a migration is genuinely required, explain why and implement the smallest safe migration consistent with current repository conventions.

Required implementation

1. Canonical repository implementation

Implement a Drizzle-backed repository that satisfies the Phase C2 discovery repository contract.

Suggested location:

lib/db/src/discovery/drizzle-discovery-repository.ts

Use the existing database client and transaction abstractions. Do not create an independent connection layer.

The repository must support, as required by the Phase C2 interface:

* Persisting discovery runs
* Persisting normalized signals
* Persisting clusters
* Persisting scored opportunities
* Reading a discovery run by ID
* Listing runs by client/tenant
* Reading signals, clusters, and opportunities for a run
* Upserting or safely deduplicating deterministic entities
* Updating run completion status and summary
* Recording partial provider failure metadata
* Atomic persistence where appropriate
* Idempotent replay of the same deterministic run

Adapt exact method names to the existing Phase C2 repository interface rather than inventing a parallel abstraction.

2. Persistence model

Persist the canonical Phase C2 data without leaking provider-specific raw response structures into the canonical tables.

The persistence layer should represent:

* Discovery run identity
* clientId
* Context snapshot or safely versioned context metadata
* Run status
* ISO week
* Start/completion timestamps
* Provider execution outcomes
* Run summary
* Canonical normalized signals
* Canonical clusters
* Canonical scorecards
* Canonical opportunities
* Registry-gate status
* Evidence strength
* Deterministic IDs
* Created/updated timestamps

Provider raw payloads should only be stored when an existing safe JSON metadata pattern supports them. Canonical business logic must not depend on stored raw payloads.

3. Tenant isolation

Every repository read and write must be tenant-scoped.

A caller must never be able to retrieve or mutate another client’s:

* Runs
* Signals
* Clusters
* Opportunities
* Provider execution records
* Summaries

Do not rely exclusively on globally unique IDs for isolation. Include clientId in repository predicates and ownership checks.

4. Pipeline integration

Integrate the Drizzle repository with the existing Phase C2 DiscoveryPipeline through dependency injection.

Requirements:

* Pure discovery functions remain pure.
* The pipeline must continue to work with an in-memory/fake repository in tests.
* Persistence failures must be represented correctly in run status and diagnostics.
* Provider failures must still yield a partial run instead of crashing the entire pipeline.
* Avoid double-writing during retries.
* Do not introduce hidden global database state.
* No external provider APIs may be called.

5. Idempotency and determinism

The same client, context, inputs, and deterministic run identity must not create duplicate canonical records.

Define and test the idempotency behavior explicitly for:

* Replayed runs
* Duplicate normalized signals
* Duplicate clusters
* Duplicate opportunities
* Partial runs retried after persistence interruption
* Concurrent or near-concurrent writes where supported by current DB patterns

Use existing deterministic Phase C2 IDs wherever possible.

6. Transaction behavior

Use transactions where needed to prevent partially persisted canonical state.

Clearly define behavior when failure occurs during:

* Run creation
* Signal persistence
* Cluster persistence
* Opportunity persistence
* Run finalization

A failed transaction must not leave misleading “completed” state.

7. Serialization boundary

Create explicit serialization/deserialization helpers when canonical TypeScript objects contain values that should not be written directly to JSON or database columns.

Round-trip persistence must preserve all canonical values required by Phase C2 scoring, summaries, diagnostics, and future Phase C4 consumers.

Avoid unsafe as casting when parsing JSON-backed columns. Validate persisted JSON using existing Zod/schema conventions where available.

8. Test boundary

No tests may require live external APIs.

Prefer the project’s existing database test conventions. If the repository test system uses mocks or an in-memory adapter, follow that pattern. Do not introduce a completely different database testing framework unless unavoidable.

Required tests

R. Persistence failure tolerance

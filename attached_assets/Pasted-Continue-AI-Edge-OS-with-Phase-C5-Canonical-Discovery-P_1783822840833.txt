Primary objective

Build the next production layer of the canonical discovery system by expanding provider capabilities, enriching canonical opportunities, and hardening orchestration for multi-provider execution—without introducing UI, scheduling, publishing, or autonomous content generation.

Phase C5 must preserve the provider-agnostic Phase C2 core and the persistence foundation from Phase C3. Live-provider adapters must remain replaceable, isolated, tenant-safe, cost-aware, and testable without external network access.

Begin with an audit-first workflow. Before changing code:

1. Read the Phase C1 architecture document.
2. Read all Phase C2 through C4 discovery source files and tests.
3. Audit the current DataForSEO adapter against the provider contracts and pipeline stages.
4. Inspect current discovery persistence tables and repository methods.
5. Search the repository for existing competitor, keyword, SERP, trend, social, analytics, content-gap, and opportunity-enrichment logic.
6. Audit current route authentication, tenant resolution, diagnostics, logging, rate limiting, and error handling.
7. Identify which Phase C2 pipeline stages remain stubbed, weakly implemented, or dependent on placeholder data.
8. Produce a concise implementation plan and proposed file changes before editing code.

Do not create duplicate provider, scoring, repository, or diagnostics abstractions when existing ones can be extended.

Required implementation

1. Complete the canonical DataForSEO provider boundary

Audit and complete the adapter so that each implemented method maps cleanly to a canonical provider interface.

At minimum, support production-capable retrieval for:

* Keyword metrics
* Search volume
* Keyword difficulty or competition proxy
* Organic SERP results
* Ranking URLs and domains
* People Also Ask questions
* Related searches or keyword suggestions where supported
* Competitor domains
* Competitor keywords when supported by the selected DataForSEO endpoint
* Geographic and language targeting
* Desktop/mobile selection where appropriate

Do not force one API response shape into every canonical provider type. Use explicit mapping functions and endpoint-specific raw types.

If DataForSEO cannot reliably provide one capability, represent it honestly as unsupported rather than synthesizing misleading data.

2. Provider capability registry

Introduce a canonical capability description for discovery providers.

The system should be able to determine whether a provider supports capabilities such as:

* Search volume
* Keyword difficulty
* SERP results
* PAA
* Related searches
* Competitor domains
* Competitor keywords
* Trend history
* Social signals
* Local-pack results
* Device targeting
* Geographic targeting
* Language targeting

Capability checks must occur before execution so unsupported calls are skipped deterministically and reported in diagnostics.

Avoid hardcoding DataForSEO checks throughout the pipeline. The pipeline should reason from provider capabilities.

3. Multi-provider orchestration

Extend the discovery orchestration so multiple provider adapters can be injected for the same canonical capability.

Implement deterministic provider selection and fallback behavior based on:

* Enabled state
* Health state
* Supported capability
* Configured tenant or system policy
* Estimated request cost
* Priority
* Previous failure state during the run
* Explicit execution mode

Support at least these orchestration modes:

* primary_only
* fallback
* merge

Behavior must be explicit:

* primary_only: execute only the selected primary provider
* fallback: try providers in deterministic order until one succeeds
* merge: execute all eligible providers and combine canonical results

No nondeterministic provider ordering is allowed.

4. Canonical result merging

Implement provider-independent merge logic for signals retrieved from multiple sources.

The merger must:

* Preserve deterministic IDs
* Deduplicate equivalent signals
* Retain provider provenance
* Prefer stronger or more complete evidence
* Preserve conflicting evidence in diagnostics when needed
* Avoid inflating evidence strength merely because duplicate providers returned the same fact
* Remain tenant-scoped
* Be deterministic regardless of asynchronous response order

Do not put provider names into canonical entity identities unless the entity is genuinely provider-specific.

5. Opportunity enrichment

Extend canonical opportunity construction with richer evidence available from C4/C5 providers.

Potential enrichment dimensions include:

* Search volume
* Keyword competition
* Current ranking presence
* Ranking position
* Competitor coverage
* PAA coverage
* Related-query breadth
* Local intent strength
* Commercial intent
* Evidence freshness
* Evidence-source diversity
* Geographic relevance
* Existing-site coverage or gap state
* Service registry eligibility
* Educational-only status

Preserve the existing Phase C2 scorecard contract unless a versioned extension is required.

If the scorecard changes:

* Version it explicitly.
* Preserve backward compatibility for persisted C2/C3 records.
* Add safe deserialization for old and new versions.
* Do not silently reinterpret historical scores.

6. Existing-site coverage boundary

Create a provider-independent interface for determining whether a client already has meaningful coverage for a discovered topic.

The boundary may consume:

* Known client URLs
* Existing content inventory
* Search Console data in a future phase
* Repository-backed content records
* Injected test fixtures

For C5:

* Use existing repository or content inventory data if available.
* Do not require Google Search Console OAuth.
* Do not crawl the public web unless an approved provider already supplies the data.
* Return explicit states such as covered, partial, gap, and unknown.

Use this state to enrich opportunities without initiating content generation.

7. Cost accounting

Implement canonical provider cost accounting.

For each provider execution, record:

* Provider
* Capability
* Endpoint or operation class
* Estimated cost
* Actual cost when supplied by the provider
* Request count
* Retry count
* Success/failure
* Tenant/client ID
* Discovery run ID

Cost data should integrate with Phase C3 persistence where the current schema supports it. If schema changes are required, use the smallest safe migration and explain why.

No provider call should occur without a deterministic cost estimate or an explicit unknown cost state.

8. Budget guard

Add an injectable budget-policy boundary that can prevent or limit provider execution.

Support:

* Per-run estimated-cost ceiling
* Per-client configurable ceiling
* Capability-specific allowance or denial
* Maximum request count
* Dry-run planning mode
* Explicit override for authorized internal testing

When a request is blocked by budget policy:

* Do not call the provider.
* Record a structured diagnostic.
* Preserve partial-run behavior.
* Do not misreport the provider as failed.

Do not build billing UI or payment processing.

9. Retry and error classification

Harden provider execution with explicit handling for:

* Authentication errors
* Authorization errors
* Invalid request errors
* Rate limits
* Quota exhaustion
* Temporary provider errors
* Timeouts
* Network failures
* Malformed responses
* Unsupported capabilities
* Budget rejection
* Disabled or unconfigured provider state

Retry only errors that are genuinely retryable.

Use deterministic bounded retry behavior. Do not use unbounded retries or random jitter in tests. Injectable delay/backoff behavior is preferred.

10. Manual-run route hardening

Audit and strengthen the existing manual discovery route.

Requirements:

* Clerk authentication
* Canonical client resolution
* Tenant ownership validation
* Request schema validation
* Explicit execution mode
* Optional dry-run plan
* Optional cost ceiling within authorized limits
* No arbitrary provider credential input
* No caller-controlled tenant bypass
* Structured response with run ID, status, provider outcomes, estimated/actual cost, and diagnostics
* Safe handling of disabled or unconfigured providers
* No sensitive credential leakage
* No raw provider payload leakage

Use existing API schema and Zod patterns if the project has a canonical API contract for internal routes.

11. Health and diagnostics

Extend discovery health reporting to show:

* Provider configured state
* Provider enabled state
* Provider health state
* Supported capabilities
* Execution priority
* Cost-estimation availability
* Budget-policy readiness
* Repository readiness
* Schema/bootstrap readiness
* Last safe diagnostic when available

Do not expose login names, passwords, authorization headers, or raw provider responses.

12. Persistence compatibility

Persist new provider outcomes, provenance, cost accounting, coverage state, and diagnostics through the Phase C3 repository boundary.

Requirements:

* Existing C2/C3 records must remain readable.
* Tenant predicates remain mandatory.
* Replays must remain idempotent.
* Provider execution records must not duplicate on retry.
* Merge-mode results must remain deterministic.
* Partial provider success must be distinguishable from total run failure.
* Historical runs must not change when provider capability configuration changes later.

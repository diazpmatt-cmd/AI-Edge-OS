Primary objective

Build the operational governance and observability layer required to run canonical discovery safely in production.

Phase C6 should make discovery runs inspectable, cancellable where technically safe, rate-limited, concurrency-controlled, auditable, and recoverable without introducing autonomous scheduling, user-facing dashboards, content generation, or publishing.

The system must remain deterministic, tenant-isolated, provider-agnostic, cost-aware, and safe under retries, duplicate requests, partial failures, and concurrent execution.

Begin with an audit-first workflow. Before editing code:

1. Read the Phase C1 architecture document.
2. Read all Phase C2–C5 discovery source files and tests.
3. Audit the current discovery-run persistence schema and repository methods.
4. Audit API-server authentication, tenant resolution, request tracing, logging, rate limiting, error middleware, and route conventions.
5. Search for existing job, execution, lock, idempotency, audit-log, activity-log, diagnostics, health, and cancellation abstractions.
6. Inspect database transaction and advisory-lock patterns already used in the monorepo.
7. Identify current gaps in run visibility, lifecycle transitions, concurrency control, duplicate manual requests, and operational recovery.
8. Produce a concise implementation plan and proposed file changes before writing code.

Reuse existing infrastructure where possible. Do not create a second job system, logging framework, or lock abstraction if one already exists.

Required implementation

1. Canonical run lifecycle

Define and enforce a canonical lifecycle for discovery runs.

At minimum, support explicit states equivalent to:

* planned
* queued
* running
* partial
* completed
* failed
* cancel_requested
* cancelled

Adapt names only if the existing canonical types already define equivalent states.

Create a centralized transition policy so invalid state changes are rejected deterministically.

Examples:

* planned → running may be allowed for synchronous manual runs.
* running → completed may be allowed.
* running → partial may be allowed.
* running → cancel_requested may be allowed.
* completed → running must not be allowed.
* cancelled → completed must not be allowed.
* Replaying a completed deterministic run must not silently restart it.

Lifecycle rules must not be duplicated across routes and repositories.

2. Run transition history

Persist an append-only transition history for every discovery run.

Each transition record should include:

* Deterministic transition ID
* Discovery run ID
* Client ID
* Previous state
* New state
* Reason code
* Safe human-readable message
* Actor type
* Actor identifier when available
* Correlation/request ID
* Timestamp
* Structured metadata
* Version or sequence number

Actor types may include:

* system
* user
* provider
* recovery
* test

Do not persist secrets, authorization headers, provider credentials, or raw provider responses.

Transition records must be tenant-scoped and append-only.

3. Execution lease and concurrency control

Implement a canonical execution-lease boundary to prevent unsafe duplicate execution.

Requirements:

* At most one active execution lease per deterministic run identity.
* Optionally enforce a configurable maximum number of active runs per client.
* Lease acquisition must be atomic.
* Lease renewal must be supported if the execution model requires it.
* Expired leases must be safely recoverable.
* Lease release must occur on terminal completion where possible.
* A crashed process must not permanently block future recovery.
* Lease ownership must be explicit.
* A caller must not release another process’s lease without an authorized recovery path.

Prefer existing PostgreSQL locking or transactional patterns if available.

Do not introduce Redis unless the project already depends on it and the audit demonstrates it is the correct existing abstraction.

4. Idempotent manual execution requests

Harden manual execution so duplicate requests do not create duplicate runs or duplicate provider charges.

Support an idempotency key supplied through an approved request header or body field, following existing API conventions.

Requirements:

* Idempotency must be scoped by client and operation.
* The same key and equivalent request should return the original result or active run reference.
* The same key with materially different input must be rejected.
* Idempotency records must have a safe retention policy or expiry field.
* Concurrent requests with the same key must resolve atomically.
* Dry-run requests must not collide incorrectly with live-run requests.
* Idempotency keys must not become globally cross-tenant.

Do not trust a client-supplied run ID as an idempotency mechanism.

5. Cancellation boundary

Add a safe cancellation boundary.

For synchronous provider calls that cannot be interrupted reliably, cancellation may be cooperative rather than immediate.

Requirements:

* Allow an authenticated authorized user to request cancellation of their own client’s active run.
* Persist cancel_requested.
* Check cancellation between pipeline stages and before each new provider operation.
* Do not start new provider calls after a cancellation request is observed.
* Preserve already persisted canonical data.
* Record whether cancellation occurred before execution, during provider execution, during persistence, or during finalization.
* End in cancelled when cancellation was honored.
* Do not falsely claim an in-flight external request was terminated if it could not actually be interrupted.
* Terminal runs must reject cancellation requests safely.

Use an injectable cancellation token or cancellation-check interface so pure functions remain pure.

6. Run progress model

Define a canonical progress snapshot for operational visibility.

Include fields such as:

* Current stage
* Completed stages
* Total stages
* Percent complete
* Current capability
* Current provider
* Signals collected
* Clusters built
* Opportunities created
* Provider calls attempted
* Provider calls completed
* Estimated cost
* Actual cost
* Last transition
* Last updated timestamp

Progress must be derived from canonical pipeline stages, not arbitrary UI percentages.

Persist progress only where operationally useful. Avoid excessive writes for every small loop iteration.

7. Structured diagnostics

Create a canonical diagnostic-event model.

Each event should support:

* Severity: info, warning, error
* Stable diagnostic code
* Safe message
* Stage
* Provider
* Capability
* Retryability
* Tenant/client ID
* Run ID
* Correlation ID
* Timestamp
* Structured safe metadata

Implement redaction or allowlisting so diagnostics cannot leak:

* Credentials
* Basic Auth headers
* Clerk tokens
* Cookies
* Database URLs
* Raw provider payloads
* Full customer content
* Internal stack traces in API responses

Internal logs may retain stack traces according to existing logging policy, but public/internal API responses must expose only sanitized diagnostics.

8. Correlation and request tracing

Add correlation identifiers across:

* Manual-run request
* Discovery run
* Provider execution records
* Cost records
* Transition history
* Diagnostic events
* API response

Use existing request IDs if the API server already supplies them.

Otherwise, create a deterministic or standards-compliant identifier using the project’s existing ID utility. Do not use Math.random().

Do not allow a caller to spoof trusted internal correlation metadata without validation.

9. Per-client concurrency policy

Implement an injectable execution-governance policy.

Support:

* Maximum active runs per client
* Maximum active provider operations per run
* Maximum active provider operations per client
* Whether merge mode may execute providers concurrently
* Whether expensive capabilities require serial execution
* Whether a client is temporarily paused
* Internal authorized override

Default to conservative execution.

Concurrency ordering must remain deterministic even if implementation uses parallel promises.

10. Rate limiting

Audit existing API rate-limiting middleware and apply it to manual discovery operations.

At minimum, distinguish:

* Health checks
* Dry-run planning
* Live manual runs
* Cancellation requests
* Run-status reads

Rate limits should be scoped using authenticated actor and client where possible.

Do not rely solely on IP addresses for authenticated multi-tenant actions.

When rate limited:

* Do not call providers.
* Do not acquire an execution lease unnecessarily.
* Return a structured safe error.
* Record a diagnostic or audit event where appropriate.

11. Run inspection API

Add authenticated tenant-safe internal endpoints for run inspection.

Suggested capabilities:

* List recent runs for the resolved client
* Read one run
* Read run progress
* Read provider outcomes
* Read cost summary
* Read sanitized diagnostics
* Read transition history
* Request cancellation

Follow existing route and API-contract conventions.

Do not add UI.

Every lookup must include clientId ownership predicates. Globally unique run IDs are not sufficient authorization.

12. Recovery boundary

Implement recovery logic for stale nonterminal runs.

Support detection of:

* Expired execution lease
* running run with no active lease
* cancel_requested run abandoned before finalization
* Persistence interruption
* Provider execution recorded but run not finalized
* Transition sequence gap or invalid state

Recovery must be explicit and safe.

Possible recovery outcomes:

* Resume from a safe checkpoint
* Mark partial
* Mark failed
* Honor pending cancellation
* Release stale lease
* Require manual intervention

Do not automatically repeat provider calls unless idempotency and cost safety are guaranteed.

For C6, prefer conservative reconciliation over aggressive automatic replay.

13. Audit boundary

Create or extend an append-only audit boundary for sensitive discovery actions:

* Manual live run requested
* Dry run requested
* Budget override used
* Governance override used
* Cancellation requested
* Recovery invoked
* Run read by privileged internal actor if existing audit policy requires it
* Provider configuration health checked
* Execution denied by tenant ownership, budget, rate limit, or concurrency policy

Reuse the existing audit-log system if one exists.

Audit events must not contain credentials or raw payloads.

14. Persistence compatibility

Extend the Phase C3 persistence layer only as required for:

* Transition history
* Execution leases
* Idempotency records
* Progress snapshots
* Diagnostic events
* Cancellation state
* Recovery metadata
* Correlation IDs
* Audit references

Use the smallest safe schema changes.

Requirements:

* Existing C2–C5 records remain readable.
* Existing completed runs do not require destructive backfills.
* New optional fields have safe defaults.
* Tenant isolation remains mandatory.
* Historical provider outcomes and scorecards retain their original meaning.
* New lifecycle validation does not corrupt old records with legacy statuses.

If migrations are required, explain each table, index, constraint, and uniqueness rule.

N. Cancellation request

Constraints

Do not build:

* UI or dashboards
* Scheduler or cron jobs
* Autonomous recurring discovery
* Background job infrastructure unless an existing system must be reused for the execution lease abstraction
* Content generation
* Content drafting
* Content publishing
* Campaign execution
* Provider credential management UI
* Billing or payment processing
* Google Search Console OAuth
* Social-platform OAuth
* User-facing notification systems

Do not:

* Modify BB&B autopilot safety state
* Enable termite services
* Represent whole-home bed bug heat treatment as offered
* Remove fumigation
* Hardcode BB&B into canonical governance logic
* Use Math.random()
* Use live external APIs in automated tests
* Store credentials in diagnostics, audit logs, idempotency records, or transition metadata
* Trust caller-supplied client IDs without canonical tenant resolution
* Authorize by run ID alone
* Restart completed runs
* Repeat chargeable provider operations during recovery without proof of safety
* Allow cancellation to corrupt persisted canonical records
* Leak stack traces through API responses
* Create duplicate logging, audit, lock, or rate-limit frameworks
* Introduce Redis solely for this phase without a demonstrated existing architectural need
* Add hidden global execution state

Primary objective

Build the operational governance and observability layer required to run canonical discovery safely in production.

Phase C6 ensures discovery runs are inspectable, cancellable where technically safe, rate-limited, concurrency-controlled, auditable, and recoverable without introducing autonomous scheduling, user-facing dashboards, content generation, or publishing.

The system must remain deterministic, tenant-isolated, provider-agnostic, cost-aware, and safe under retries, duplicate requests, partial failures, and concurrent execution.

Reuse existing infrastructure where possible. Do not create a second job system, logging framework, or lock abstraction if one already exists.

Required implementation

1. Canonical run lifecycle

Define and enforce a canonical lifecycle for discovery runs.

At minimum, support explicit states equivalent to:

* planned
* queued
* running
* partial
* completed
* failed
* cancel_requested
* cancelled

Adapt names only if equivalent states already exist.

Create a centralized transition policy so invalid state changes are rejected deterministically.

Examples:

* planned → running may be allowed for synchronous manual runs.
* running → completed may be allowed.
* running → partial may be allowed.
* running → cancel_requested may be allowed.
* completed → running must not be allowed.
* cancelled → completed must not be allowed.
* Replaying a completed deterministic run must not silently restart it.

Lifecycle rules must not be duplicated across routes and repositories.

2. Run transition history

Persist an append-only transition history for every discovery run.

Each transition record must include:

* Deterministic transition ID
* Discovery run ID
* Client ID
* Previous state
* New state
* Reason code
* Safe human-readable message
* Actor type
* Actor identifier when available
* Correlation/request ID
* Timestamp
* Structured metadata
* Version or sequence number

Actor types may include:

* system
* user
* provider
* recovery
* test

Do not persist secrets, authorization headers, provider credentials, or raw provider responses.

Transition records must be tenant-scoped and append-only.

3. Execution lease and concurrency control

Implement a canonical execution-lease boundary to prevent unsafe duplicate execution.

Requirements:

* At most one active execution lease per deterministic run identity.
* Optionally enforce a configurable maximum number of active runs per client.
* Lease acquisition must be atomic.
* Lease renewal must be supported if required.
* Expired leases must be safely recoverable.
* Lease release must occur on terminal completion where possible.
* A crashed process must not permanently block recovery.
* Lease ownership must be explicit.
* A caller must not release another process’s lease without authorization.

Prefer existing PostgreSQL locking or transactional patterns if available.

Do not introduce Redis unless already used and justified by the audit.

4. Idempotent manual execution requests

Ensure duplicate requests do not create duplicate runs or provider charges.

Support idempotency keys via approved headers or body fields.

Requirements:

* Scoped by client and operation.
* Same key + equivalent request returns original result.
* Same key + different input is rejected.
* Records include retention/expiry.
* Concurrent identical requests resolve atomically.
* Dry-run and live-run requests remain distinct.
* Keys must not collide across tenants.

Do not trust client-supplied run IDs as idempotency.

5. Cancellation boundary

Add a safe cancellation boundary.

Requirements:

* Authorized users can cancel their own active runs.
* Persist cancel_requested.
* Check cancellation between stages and before provider calls.
* Do not start new provider calls after cancellation is observed.
* Preserve persisted data.
* Record cancellation timing context.
* End in cancelled when honored.
* Do not falsely claim interruption of in-flight external calls.
* Terminal runs reject cancellation safely.

Use an injectable cancellation token interface.

6. Run progress model

Define a canonical progress snapshot.

Include:

* Current stage
* Completed stages
* Total stages
* Percent complete
* Current capability
* Current provider
* Signals collected
* Clusters built
* Opportunities created
* Provider calls attempted/completed
* Estimated and actual cost
* Last transition
* Last updated timestamp

Progress must derive from canonical pipeline stages.

Avoid excessive persistence writes.

7. Structured diagnostics

Create a canonical diagnostic-event model.

Each event includes:

* Severity (info, warning, error)
* Stable diagnostic code
* Safe message
* Stage
* Provider
* Capability
* Retryability
* Tenant/client ID
* Run ID
* Correlation ID
* Timestamp
* Structured safe metadata

Ensure redaction of:

* Credentials
* Auth headers
* Tokens
* Cookies
* Database URLs
* Raw payloads
* Customer content
* Stack traces in API responses

Internal logs may retain stack traces per policy.

8. Correlation and request tracing

Add correlation identifiers across:

* Requests
* Runs
* Provider executions
* Cost records
* Transitions
* Diagnostics
* API responses

Use existing request IDs or deterministic ID utilities.

Do not use Math.random().

Prevent spoofing of trusted metadata.

9. Per-client concurrency policy

Implement an injectable governance policy supporting:

* Max active runs per client
* Max provider operations per run/client
* Merge-mode concurrency rules
* Serial execution for expensive capabilities
* Client pause state
* Authorized overrides

Maintain deterministic ordering.

10. Rate limiting

Apply rate limiting to discovery operations.

Distinguish:

* Health checks
* Dry runs
* Live runs
* Cancellation
* Inspection

Scope limits by authenticated actor and client.

When limited:

* Do not call providers
* Do not acquire leases unnecessarily
* Return safe structured errors
* Record diagnostics/audit events

11. Run inspection API

Provide authenticated tenant-safe endpoints:

* List runs
* Read run details
* Read progress
* Read provider outcomes
* Read cost summary
* Read diagnostics
* Read transitions
* Request cancellation

All queries must enforce clientId ownership.

No UI.

12. Recovery boundary

Implement recovery for stale runs.

Detect:

* Expired leases
* Running runs without leases
* Abandoned cancellations
* Persistence interruptions
* Incomplete finalization
* Invalid transitions

Recovery actions:

* Resume safely
* Mark partial/failed
* Honor cancellation
* Release leases
* Require manual intervention

Do not repeat provider calls unless safe.

Prefer conservative reconciliation.

13. Audit boundary

Extend append-only audit logging for:

* Run requests (live/dry)
* Overrides
* Cancellation
* Recovery
* Inspection (if required)
* Denials (auth, budget, rate, concurrency)

Reuse existing audit systems.

Never store credentials or raw payloads.

14. Persistence compatibility

Extend persistence minimally for:

* Transitions
* Leases
* Idempotency
* Progress
* Diagnostics
* Cancellation
* Recovery metadata
* Correlation IDs
* Audit references

Requirements:

* Backward compatibility with C2–C5
* No destructive migrations
* Safe defaults
* Tenant isolation preserved
* Historical data integrity maintained

Document all schema changes.

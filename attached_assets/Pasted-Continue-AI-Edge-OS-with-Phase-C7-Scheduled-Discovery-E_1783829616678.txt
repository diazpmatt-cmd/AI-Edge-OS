Primary objective

Build the production-safe automation layer that can schedule recurring discovery runs, reconcile stale executions, and dispatch governed discovery work through the existing C6 lifecycle, lease, idempotency, budget, cancellation, and audit boundaries.

Phase C7 must not create a second execution system. It must orchestrate the canonical pipeline through the infrastructure already established in C2–C6.

The automation layer must remain:

* Tenant-isolated
* Deterministic
* Cost-aware
* Lease-protected
* Idempotent
* Auditable
* Recoverable
* Provider-agnostic
* Safe under multiple server instances
* Disabled by default until explicitly configured

Do not build UI, content generation, publishing, campaign execution, or unrestricted background processing.

Required implementation

1. Canonical discovery schedule model

Define a canonical tenant-scoped schedule model.

A schedule should support:

* Deterministic schedule ID
* Client ID
* Human-readable name
* Enabled state
* Execution mode
* Provider policy reference or snapshot
* Discovery context configuration
* Frequency or cron representation
* IANA timezone
* Next-run time
* Last-run time
* Last successful run time
* Consecutive failure count
* Maximum estimated cost per run
* Maximum requests per run
* Catch-up policy
* Overlap policy
* Pause reason
* Created and updated timestamps
* Created-by and updated-by actor metadata
* Optimistic version or revision number

Use existing cron/date libraries when available. Do not implement a custom cron parser when a trusted dependency or existing utility already exists.

Schedules must be tenant-scoped in every read and write predicate.

2. Schedule lifecycle

Support explicit schedule states or equivalent fields for:

* Active
* Paused
* Disabled
* Archived
* Error-blocked

Define centralized transition rules.

Examples:

* Disabled schedules cannot dispatch runs.
* Paused schedules retain configuration but do not advance through normal execution.
* Error-blocked schedules require a documented recovery or manual re-enable action.
* Archived schedules cannot be reactivated without an explicit supported transition.
* Temporary provider unavailability should not automatically archive a schedule.

Every schedule transition must produce a sanitized audit event.

3. Schedule calculation

Implement deterministic next-run calculation.

Requirements:

* Respect the configured IANA timezone.
* Handle daylight-saving transitions safely.
* Handle invalid or nonexistent local times according to documented policy.
* Avoid double execution during repeated DST hours.
* Support at least hourly, daily, weekly, and valid cron-based schedules if consistent with existing dependencies.
* Persist next-run timestamps in UTC.
* Preserve timezone and original scheduling intent.
* Do not depend on process-local timezone.
* Provide an injectable clock for tests.
* Do not use Math.random().

Document behavior for missed executions and server downtime.

4. Scheduler leadership

Ensure multiple API-server instances cannot dispatch the same due schedule simultaneously.

Implement or reuse a scheduler-leadership boundary with:

* Atomic leadership acquisition
* Lease expiry
* Lease renewal or heartbeat
* Explicit owner identity
* Safe takeover after owner failure
* Protection against release by the wrong owner
* Configurable lease duration
* Disabled state when automation is not configured

Scheduler leadership must be separate from individual discovery-run execution leases.

Do not depend solely on an in-memory singleton or process-local boolean.

5. Due-schedule claiming

Implement atomic claiming of due schedules.

Requirements:

* A due schedule is claimed by at most one dispatcher.
* Claiming and next-run advancement must avoid duplicate dispatch.
* Claims must expire if the dispatcher crashes.
* Claims must retain correlation and ownership metadata.
* Tenant boundaries must remain intact.
* Claim ordering must be deterministic.
* A large tenant must not permanently starve other tenants.
* Disabled, paused, archived, or error-blocked schedules must not be claimed.
* Schedules with an active overlapping run must follow their overlap policy.

Prefer transactional row locking or an equivalent existing PostgreSQL pattern.

6. Overlap policies

Support explicit overlap behavior:

* skip
* queue_one
* allow

Default to skip unless existing architecture dictates otherwise.

Behavior:

* skip: record a skipped occurrence and calculate the next run.
* queue_one: retain at most one pending occurrence.
* allow: dispatch only when client and provider concurrency governance permits it.

Do not allow schedule overlap rules to bypass C6 execution-governance limits.

7. Catch-up policies

Support explicit missed-run behavior after downtime:

* skip_missed
* run_latest
* run_all_bounded

For run_all_bounded:

* Require a configurable maximum catch-up count.
* Apply current budget and governance policies.
* Preserve the intended occurrence timestamp.
* Use a unique idempotency identity per scheduled occurrence.
* Dispatch occurrences in deterministic chronological order.

Never replay an unbounded backlog.

8. Scheduled-run idempotency

Derive a deterministic scheduled-occurrence identity from at least:

* Client ID
* Schedule ID
* Intended occurrence time
* Execution mode
* Material schedule revision

The same occurrence must not create duplicate discovery runs or duplicate provider costs.

Requirements:

* Multiple dispatcher instances converge on one run.
* Retrying dispatch after a timeout returns the existing run reference.
* A schedule revision must not silently alter an already-created occurrence.
* Dry-run schedules and live schedules remain distinct.
* Manual runs must not collide with scheduled occurrences.
* Idempotency remains tenant-scoped.

Reuse the C6 idempotency boundary rather than creating a parallel mechanism.

9. Governed dispatcher

Create a canonical scheduled-discovery dispatcher that routes work through existing boundaries in this order, adapted to current architecture:

1. Verify automation feature state.
2. Resolve schedule and tenant ownership.
3. Verify schedule is eligible.
4. Establish correlation metadata.
5. Check idempotency.
6. Apply client pause and governance rules.
7. Apply concurrency limits.
8. Calculate provider plan and estimated cost.
9. Apply budget policy.
10. Create or recover the canonical run.
11. Acquire the run execution lease.
12. Write audit and lifecycle transitions.
13. Execute the canonical discovery pipeline.
14. Persist costs, diagnostics, progress, and transitions.
15. Finalize the run.
16. Release the run lease.
17. Update schedule success/failure metadata.
18. Advance the next-run time.

No scheduled run may bypass C5 budget protections or C6 governance.

Do not activate recurring production calls merely because DataForSEO credentials exist.

11. Scheduler tick boundary

Implement a testable single-tick function.

A scheduler tick should:

* Attempt leadership acquisition.
* Find due schedules.
* Claim a bounded number.
* Dispatch eligible occurrences.
* Record per-schedule outcomes.
* Release or renew leadership safely.
* Return a structured summary.
* Never throw away all results because one schedule failed.
* Avoid live timers in unit tests.

The core tick must be callable directly in tests without starting a background loop.

12. Runtime loop integration

Integrate the scheduler loop into the existing API-server runtime only if consistent with current architecture.

Requirements:

* Start only when explicitly enabled.
* Do not start during tests unless injected and requested.
* Do not start during build scripts or migrations.
* Prevent duplicate local loops within one process.
* Stop cleanly on shutdown signals.
* Avoid unhandled promise rejections.
* Use bounded execution.
* Emit sanitized operational diagnostics.
* Do not block API-server startup indefinitely.

Keep loop control thin; business logic belongs in testable library functions.

13. Automated stale-run recovery

Wire the C6 stale-run recovery boundary into a governed recovery scan.

The recovery scan should detect:

* Expired execution leases
* Running runs without active leases
* Abandoned cancel_requested runs
* Runs interrupted during persistence or finalization
* Claimed schedule occurrences with no run
* Scheduler claims abandoned by dead owners

Recovery actions must be conservative:

* Honor pending cancellation.
* Release stale leases when safe.
* Mark partial or failed when provider replay is unsafe.
* Resume only from an explicitly safe checkpoint.
* Never repeat a chargeable provider call without idempotent proof.
* Record recovery transitions, diagnostics, and audit events.
* Preserve tenant isolation.

14. Schedule failure policy

Implement deterministic handling for repeated failures.

Support:

* Consecutive failure counter
* Configurable pause/error threshold
* Retry at next normal occurrence
* Temporary exponential or stepped delay if consistent with architecture
* Maximum delay cap
* Reset after successful completion
* Error-blocking for invalid configuration or permanent authorization failures
* No automatic disabling for a single transient provider error

Do not use random retry jitter in deterministic tests.

Separate:

* Schedule configuration failures
* Tenant/governance denials
* Budget denials
* Provider transient failures
* Provider permanent failures
* Persistence failures
* Cancellation
* Skipped overlap occurrences

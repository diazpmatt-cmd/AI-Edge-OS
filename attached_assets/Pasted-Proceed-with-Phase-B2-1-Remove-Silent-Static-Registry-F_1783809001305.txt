Proceed with Phase B2.1 — Remove Silent Static Registry Fallback and Finalize Phase B2 Validation.

Phase B2 has been implemented, but one tenant-safety issue remains.

Current concerning behavior:

resolveClientContentContextFromDb() loads the database-backed registry but falls back to the static provider when:

- Registry seeding is delayed
- Registry rows are missing
- Registry loading throws a database error

This silent fallback violates the Phase B2 requirements.

Objective:

Make the database-backed service registry authoritative for configured clients.

A missing, empty, corrupt, or unavailable registry must produce an explicit typed failure. It must not silently substitute bbbRegistryProvider.

Audit the exact fallback path before editing.

Required behavior:

1. Successfully seeded BB&B client

- Loads the database-backed service registry
- Uses createDbServiceRegistryProvider(...)
- Does not use bbbRegistryProvider as its production provider
- Preserves exact BB&B behavior

2. Missing registry

Return a typed result such as:

{
  found: false,
  reason: "registry_not_configured"
}

Use existing result conventions if different.

3. Invalid or empty registry

Return a typed result such as:

{
  found: false,
  reason: "registry_invalid"
}

This should cover cases such as:

- Zero service rows
- Duplicate service keys after loading
- Invalid availability values
- Missing required client registry rules
- Malformed capability data
- Structurally unusable service records

Do not overbuild validation. Add the smallest checks necessary to prevent constructing an unsafe provider.

4. Database or registry-load error

Return a typed result such as:

{
  found: false,
  reason: "registry_unavailable"
}

Do not expose internal database details to API consumers.

Log the operational error safely for diagnostics.

5. Legacy static provider usage

bbbRegistryProvider may remain only as:

- A parity oracle in tests
- A test fixture
- An explicitly named legacy helper that is not reached by normal DB-backed client resolution

Document every remaining production call site.

There must be no implicit fallback from DB-backed resolution to bbbRegistryProvider.

6. Route behavior

Verify the following routes handle typed registry failures before AI calls or writes:

- GET auto-content settings
- GET suggestions
- POST generate

Use clear status mappings, for example:

- not_found → 404
- inactive → 403
- registry_not_configured → 422
- registry_invalid → 422
- registry_unavailable → 503

Follow existing API conventions if they differ.

Do not modify PUT, pause, or resume in this correction phase.

7. Startup race behavior

The bootstrap IIFE may complete after some modules load.

Do not solve this with static-provider fallback.

Instead, choose the smallest reliable option:

- Await a shared registry-bootstrap promise before registry reads, or
- Make loadClientServiceRegistry ensure schema/bootstrap readiness, or
- Return registry_unavailable until initialization completes

Prefer awaiting one shared bootstrap promise so requests do not race table creation or seeding.

Avoid duplicate bootstrap execution.

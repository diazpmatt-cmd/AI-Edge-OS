CANONICAL MODEL

Design the smallest reusable model that supports service registries for any industry.

Prefer normalized typed tables over one large unstructured JSON blob.

At minimum, support the following concepts.

Client service record:

- id
- client_id
- stable service key
- display name
- short name if currently required
- category
- description
- active status
- availability status
- sort order
- created_at
- updated_at

Availability must support at least:

- active
- coming_soon
- unavailable

Service capability flags must support at least:

- allow_ai_generation
- allow_booking
- allow_cta
- allow_publishing
- allow_recommendation

Service topic and matching data:

- canonical topic
- aliases
- normalized aliases
- prompt rules
- prohibited wording if needed
- preferred wording if needed
- weekly planning eligibility
- default-topic eligibility

Client-level registry rules:

- system business rules
- global prohibited topics or claims
- global preferred positioning
- registry version or updated timestamp if useful

Do not add industry-specific columns such as:

- termite
- fumigation
- bed_bug
- plumbing
- roofing

Industry-specific values belong in service records and rules, not the schema.

REQUIRED IMPLEMENTATION

1. Canonical Service Registry Schema

Create or extend the minimum tables needed for:

- Client services
- Service aliases/topics
- Service prompt rules
- Client-level business rules

Use existing Drizzle and migration conventions.

Add:

- Foreign keys where supported by current conventions
- Unique constraints preventing duplicate service keys per client
- Indexes for client lookup
- Stable deterministic ordering
- Idempotent migration or bootstrap behavior

Do not make service identity depend on display-name text.

Use a stable service key.

2. BB&B Registry Backfill

Seed the canonical BB&B registry from the existing source of truth.

The backfill must be idempotent.

Running it repeatedly must not:

- Duplicate services
- Duplicate aliases
- Duplicate rules
- Change service availability incorrectly
- Enable termites
- Remove fumigation
- Enable autopilot

Preserve the existing service ordering where behavior depends on it.

3. Database-Backed Provider

Implement a reusable provider that satisfies ServiceRegistryProvider.

Use an appropriate name such as:

createDbServiceRegistryProvider(...)
or
DbServiceRegistryProvider

Follow existing project conventions.

It must support:

- matchByTopic
- validateTopic
- selectWeeklySlots
- getPromptRules
- normalizeTopics
- getDefaultTopics
- getSystemBusinessRules

Do not copy and paste BB&B-specific algorithms into the provider.

Separate:

- Generic matching and selection logic
- Database-supplied client service data
- Client-specific rules

The provider must not query the database separately for every method invocation during one request.

Load the registry once, build an in-memory provider, and reuse it for the resolved context.

4. Provider Resolution

Update the centralized registry-resolution flow so:

- BB&B resolves to its database-backed registry
- Future clients can resolve through the same generic mechanism
- Registry resolution is based on client identity and stored registry data, not an expanding hardcoded slug switch
- Missing registries return a typed result
- Empty or corrupt registries return a typed error
- Unknown clients never receive BB&B services

The legacy bbbRegistryProvider may remain temporarily as:

- A parity oracle
- A fallback only for an explicitly documented internal legacy path
- A test fixture

It must not remain the primary provider for a successfully seeded DB-backed BB&B client.

5. Resolver Integration

Update resolveClientContentContextFromDb(userId) to:

- Load the client
- Load auto-content settings
- Load the client’s service registry
- Build one database-backed provider
- Build ClientContentContext with that provider
- Return typed failure reasons when needed

Possible typed reasons include:

- not_found
- inactive
- registry_not_configured
- registry_invalid

Use existing naming conventions if different.

6. Generation-Path Integration

The auto-content generate route already consumes context.registry.

Integrate the DB-backed resolver into the generate path only if it can be done without changing generation behavior.

Requirements:

- Autopilot safety gate remains enforced
- Existing scheduler authentication remains unchanged
- No posts are published during validation

REQUIRED BEHAVIOR

1. Canonical tenant resolution

All three write paths must resolve the authenticated client through the canonical client resolver or a smaller write-safe client resolver.

Requirements:

- Unknown tenant → 404
- Inactive client → 403
- Registry not configured → 422 where registry-dependent validation is required
- Registry invalid → 422
- Registry unavailable → 503
- Never fall back to BB&B
- Never accept a client ID or user ID from the request body as authority
- The authenticated Clerk user_id remains the tenant authority in this phase

2. PUT settings

The PUT handler must:

- Resolve the authenticated client
- Read and write only that tenant’s auto_content_settings row
- Use user_id from authentication, not the request body
- Preserve existing supported settings
- Validate topics against the resolved client registry
- Normalize topics through context.registry
- Reject prohibited, coming-soon, disabled, or non-generatable topics
- Preserve approval_required behavior
- Preserve autopilot_enabled safety rules
- Prevent unknown fields from silently changing stored configuration
- Avoid creating duplicate settings rows
- Return the resolved client identity in the response where useful

Do not allow PUT settings to activate termites or other blocked BB&B services.

3. Pause

The pause handler must:

- Resolve the authenticated client
- Set only that tenant’s autopilot_enabled to false
- Be idempotent
- Never create or modify another tenant’s row
- Return a clear result if settings do not exist
- Preserve existing scheduled drafts and pending-review posts
- Not delete content
- Not publish content

Decide explicitly whether a missing settings row should:

- Return 404/422, or
- Create a safe disabled settings row

Prefer not creating implicit configuration unless that is already established behavior.

4. Resume

The resume handler must:

- Resolve the authenticated client
- Validate that settings exist
- Validate the client registry is usable
- Validate approval mode and required scheduling configuration
- Enable only that tenant’s autopilot
- Never publish immediately
- Never generate immediately unless that is existing documented behavior
- Never activate if registry resolution fails
- Never activate blocked services
- Remain idempotent

Human approval requirements must remain intact.

5. Write-path tenant isolation

Add tests proving:

- BB&B can update only BB&B settings
- Lakeside Plumbing can update only Lakeside settings
- BB&B cannot mutate Lakeside settings
- Lakeside cannot mutate BB&B settings
- Request-body user_id is ignored or rejected
- Request-body client_id is ignored or rejected
- Unknown tenants cannot write
- Inactive tenants cannot write
- Missing registries block registry-dependent writes
- Invalid registries block registry-dependent writes
- Registry-unavailable errors do not write partial changes
- Failed validation leaves the previous row unchanged
- Duplicate rows are not created

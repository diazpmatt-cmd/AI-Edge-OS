REQUIRED BEHAVIOR

1. Tenant-aware scheduler eligibility query

Create the smallest reusable query or repository function that returns scheduler-eligible clients.

A client is eligible only when:

- clients.is_active = true
- auto_content_settings.autopilot_enabled = true
- auto_content_settings.engine_paused = false
- Required scheduling configuration exists
- Client registry is configured and valid
- The tenant is due for a scheduled run

Do not include clients with:

- Missing settings
- Inactive client records
- autopilotEnabled=false
- enginePaused=true
- Missing or invalid registries
- Invalid timezone
- Invalid posting schedule

Do not hardcode BB&B or any single user ID.

2. Per-client isolated execution

The scheduler must process eligible tenants independently.

Requirements:

- One client failure must not stop other clients
- Each client gets its own context
- Each client gets its own registry
- Each client gets its own weeklyPlanId or equivalent idempotency key
- Each client writes only its own posts and plans
- Logs identify the client safely
- No cross-tenant arrays, caches, or mutable context reuse

Use bounded sequential processing or conservative concurrency.

Do not create uncontrolled parallel AI calls.

3. Scheduler authentication

Preserve scheduler authentication.

Do not weaken SCHEDULER_SECRET handling.

Ensure the scheduler can invoke generation for a specific tenant without trusting a request-body user ID from an external caller.

Prefer one of these patterns:

- Internal function call with an explicit already-resolved tenant context
- Internal authenticated request carrying a server-generated tenant identifier
- A dedicated internal route that accepts tenant identity only after scheduler-secret authentication

Do not expose a public route where arbitrary callers can select another tenant.

Document the selected trust boundary.

4. Generate-path hardening

Audit every branch of POST generate.

Remove any remaining fallback to:

- BB&B client identity
- BB&B geography
- BB&B topics
- BB&B services
- BB&B registry
- DEFAULT_SERVICE_AREAS
- DEFAULT_TOPICS

For an authenticated tenant:

- Missing client → 404
- Inactive client → 403
- Missing registry → 422
- Invalid registry → 422
- Registry unavailable → 503
- Missing settings → explicit typed error
- Invalid scheduling configuration → 422

The generate route must build its context from the canonical DB-backed resolver.

Do not call buildClientContentContext(null) for a normal authenticated tenant.

Any remaining null fallback must be restricted to a clearly documented legacy internal test path and must be unreachable from production requests.

5. Scheduler and generate eligibility rules

Define and test the exact relationship:

- autopilotEnabled=false → scheduler must skip
- enginePaused=true → scheduler must skip
- approvalMode=approval_required → generation may create pending_review content but must not publish
- approvalMode=draft_only → generation may create drafts but must not publish
- approvalMode=auto_schedule → preserve existing behavior, but do not enable it for BB&B during validation
- Missing topics → skip or typed configuration error
- Missing service areas → skip or typed configuration error
- Invalid registry → skip and log safely

Do not let scheduler execution modify autopilotEnabled or enginePaused automatically.

6. Idempotency per tenant

Preserve and strengthen the existing weekly plan guard.

Verify:

- The same tenant + same weeklyPlanId creates no duplicates
- Two different tenants may use structurally similar plan IDs without collision
- A failure after partial work cannot produce duplicate posts on retry
- Idempotency queries include tenant ownership
- Existing BB&B idempotency behavior remains unchanged

If weeklyPlanId is globally unique today, document whether tenant scoping is still explicit in queries.

Only add a migration if a real constraint problem exists.

Proceed with Phase C2 — Canonical Discovery Engine Core.

Phase C1 architecture is complete and documented at:

.local/phase-c1-discovery-architecture.md

Do not redesign the C1 architecture unless an implementation blocker is discovered and documented first.

Objective:

Implement the provider-agnostic, multi-tenant core of the Discovery Engine without connecting live external research providers yet.

This phase must establish:

- Canonical discovery data types
- Discovery context resolution
- Service-registry safety gates
- Signal normalization
- Keyword/topic clustering
- Opportunity scoring
- Priority classification
- Provider failure isolation
- Deterministic test fixtures

Do not build UI.
Do not connect live Google, Reddit, Gemini, ChatGPT, Perplexity, Bing, or trends APIs.
Do not schedule weekly production runs yet.
Do not generate or publish content.

Audit first.

Before editing, inspect:

- .local/phase-c1-discovery-architecture.md
- ClientContentContext
- ServiceRegistryProvider
- BBBService metadata
- Existing client resolver
- Existing keyword schema
- Existing AI visibility audit schema
- localPresenceChannelsTable
- Existing test conventions
- Existing repository and migration conventions

Follow the C1 document unless doing so would conflict with the current codebase.

Required implementation:

1. Canonical Discovery Types

Create the canonical typed contracts defined in Phase C1 for:

- DiscoveryContext
- DiscoverySignal
- NormalizedDiscoverySignal
- DiscoveryCluster
- DiscoveryOpportunity
- OpportunityScoreCard
- DiscoveryProviderResult
- DiscoveryRunSummary
- Provider failure/error result

Keep the contracts:

- Provider-agnostic
- Industry-agnostic
- Multi-tenant
- Serializable
- Stable enough for later database persistence

Do not put BB&B-specific values into shared interfaces.

2. Discovery Context Builder

Implement a pure function that builds DiscoveryContext from:

- ClientContentContext
- Client identity
- Service registry
- Service areas
- Region
- Industry
- Enabled services
- Scheduling or discovery configuration where relevant

The context builder must:

- Clone mutable arrays
- Avoid shared references
- Never silently fall back to BB&B for an unknown tenant
- Preserve tenant identity
- Expose only services allowed for discovery
- Exclude disabled, prohibited, and coming-soon services from actionable opportunities
- Allow educational-only services to be marked non-transactional where applicable

For BB&B:

- Termites must not become actionable
- Wildlife removal must remain excluded
- Whole-home bed bug heat treatment must remain excluded
- Fumigation may appear only within its allowed educational/awareness constraints

3. Registry Gate

Implement the Phase C1 RegistryGate as a pure function.

It must evaluate a proposed discovery topic against the resolved ServiceRegistryProvider and return a typed result such as:

- allowed
- educational_only
- blocked
- unknown
- unsupported

Do not use loose booleans if the C1 design specifies a richer result.

The result must carry a reason suitable for logs and future UI explanations.

4. Signal Normalization

Implement a provider-independent normalization function.

It must accept raw test-provider results and normalize:

- Query/topic text
- Source/provider
- Geography
- Search intent
- Service association
- Competitor association
- Trend direction
- Seasonality
- Evidence strength
- Timestamp/freshness
- URL or citation metadata where available

Normalization must be deterministic.

Do not invent search volume, ranking data, traffic, or citations.

Unknown values must remain unknown rather than being fabricated.

5. Cluster Builder

Implement the canonical clustering logic from Phase C1.

For C2, use deterministic rule-based clustering only.

Allowed techniques:

- Normalized text
- Explicit service mapping
- Intent classification
- Geography matching
- Shared entity/topic keys
- Provider-supplied semantic group identifiers in fixtures

Do not introduce embeddings, vector databases, or paid AI calls in C2.

The cluster builder must:

- Keep tenants isolated
- Prevent unrelated services from merging
- Preserve source evidence
- Deduplicate exact and near-identical fixture signals
- Produce stable cluster IDs or keys
- Remain deterministic across runs

6. Opportunity Scorer

Implement the Phase C1 scorecard with its six scoring dimensions and documented weights.

The scorer must:

- Use only available evidence
- Handle missing values explicitly
- Apply service-registry restrictions
- Apply seasonality where available
- Apply competitor-gap signals where available
- Apply source-quality tiers
- Apply freshness/decay rules if defined in C1
- Produce an explanation for every dimension
- Produce a final score and priority tier
- Apply documented priority overrides

Critical rule:

The score must not imply precision unsupported by the evidence.

Include confidence or evidence quality in the result.

7. Provider Adapter Test Boundary

Create one or more deterministic fake discovery providers implementing the C1 provider interfaces.

Fixtures should include signals resembling:

- Search query opportunity
- People Also Ask question
- Seasonal trend
- Competitor content gap
- AI-search citation observation
- Reddit/community question
- Local service-area opportunity
- Duplicate signals from multiple providers
- Provider timeout/failure
- Unsupported or malformed result

These are test fixtures only.

Do not present them as real data.
Do not persist them as production findings.

8. Fault-Tolerant Discovery Pipeline

Implement a pure or dependency-injected DiscoveryPipeline that:

- Accepts a DiscoveryContext
- Executes a supplied list of providers
- Isolates provider failures
- Continues when one provider fails
- Normalizes successful signals
- Applies the registry gate
- Builds clusters
- Scores opportunities
- Returns a typed DiscoveryRunSummary

One provider failure must not abort the entire run.

The result must clearly report:

- Providers attempted
- Providers succeeded
- Providers failed
- Signals received
- Signals accepted
- Signals blocked
- Clusters created
- Opportunities created
- High-priority opportunities
- Failure details

9. Tenant Isolation

Add tests with at least two fictional clients from different industries.

For example:

- Bed Bugs & Beyond
- Lakeside Plumbing

Prove that:

- Signals cannot cross tenant boundaries
- Service matches cannot cross registry providers
- Clusters cannot mix tenants
- Opportunity scores cannot use another tenant’s metadata
- Geography remains client-specific
- A plumbing signal cannot become a BB&B pest-control opportunity
- A pest-control signal cannot become a Lakeside plumbing opportunity

Do not add fictional clients to the production database.

Use test fixtures only.

10. Persistence Boundary

Define the repository interface or persistence boundary described in C1, but do not necessarily write production database records in C2.

The core engine must not depend directly on Drizzle or route handlers.

Use dependency injection so C3 can add persistence without rewriting the core.

11. Existing Mock Intelligence Protection

Do not connect the new engine to:

- Math.random() AI visibility scoring
- GPT-fabricated keyword volumes
- Hardcoded competitor JSON
- Existing demo score calculations

Add comments or documentation making clear that these sources are noncanonical and must not feed Discovery Engine opportunities.

Do not delete those legacy features in C2 unless removal is required for compilation.

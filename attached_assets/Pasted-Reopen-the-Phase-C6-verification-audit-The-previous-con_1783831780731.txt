Issues that must be treated as potential C6 blockers

1. Execution lease timing

The previous audit states that the execution lease is acquired only after pipeline.run() returns.

Verify the actual control flow.

If the provider pipeline executes before lease acquisition, then the lease does not prevent:

* duplicate provider requests;
* duplicate provider charges;
* simultaneous execution of the same deterministic run;
* governance-count race conditions.

This is not an acceptable “negligible TOCTOU window.” It contradicts the C6 requirement that execution leases prevent unsafe duplicate execution.

The correct order should generally be:

1. resolve tenant;
2. validate idempotency;
3. apply rate, governance, and budget checks;
4. create or resolve the canonical run;
5. acquire the run execution lease;
6. transition the run to running;
7. invoke the discovery pipeline;
8. finalize and release the lease.

If the existing code does not follow an equivalent safe order, classify it as a blocking defect and fix it.

Add a concurrency test proving two simultaneous requests cannot both invoke provider fetch functions.

2. Cooperative cancellation is not wired

The previous audit states that discovery-pipeline.ts performs no cancellation checks between stages.

That contradicts the original C6 requirements:

* check cancellation between pipeline stages;
* check before every new provider operation;
* do not start new provider calls after cancellation is observed;
* end in cancelled when cancellation is honored.

Merely writing cancel_requested to the database does not satisfy cooperative cancellation.

Verify whether a cancellation-token boundary exists and is actually injected into the pipeline and orchestrator.

If not, classify this as a blocking C6 defect and implement:

* cancellation check before Stage 1;
* cancellation check between every pipeline stage;
* cancellation check before each provider operation;
* cancellation-aware fallback and merge execution;
* safe cancellation finalization;
* tests proving no additional provider call begins after cancellation.

Do not claim that an in-flight HTTP request was terminated unless an abort signal is truly supported.

3. Process-local rate limiting

The previous audit describes the rate limiter as in-memory and not shared across instances.

Determine the actual deployment assumptions.

If the API server may run on multiple instances, process-local rate limiting does not satisfy production-safe actor/client rate limiting.

Do one of the following:

* reuse an existing shared database or distributed rate-limit implementation; or
* explicitly constrain and document C6 as single-instance only and classify multi-instance production readiness as unsupported.

Do not label the system generally production-ready while silently excluding the expected deployment model.

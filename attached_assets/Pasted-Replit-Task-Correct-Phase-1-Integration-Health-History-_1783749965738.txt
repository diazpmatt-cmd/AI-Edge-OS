Replit Task: Correct Phase 1 Integration Health History Before Phase 2

Background:

The Phase 1 audit found that GET /diagnostics/health is polled every 30 seconds and currently persists seven rows on every request.

This creates:

- 20,160 rows per day for one continuously active administrator
- unconditional duplicate snapshots
- 2,880 prune DELETE statements per day per active user
- missing OpenAPI coverage
- suboptimal indexes
- a small secret-sanitization gap for Meta/Facebook token formats

Classification:
Needs correction before Phase 2.

Goal:

Keep the Integration Health History feature, but make it efficient, secure, OpenAPI-compliant, and suitable for future:

- Morning Brief summaries
- uptime charts
- alerting
- Apollos trend analysis

Do not build Phase 2 UI yet.

Implementation requirements:

1. Add deduplicated persistence

Before inserting a provider health record, fetch the most recent record for that authenticated user and provider.

Persist a new row only when at least one meaningful field has changed:

- normalized status
- sanitized error message
- health score
- meaningful safe metadata
- last success state, where relevant

Do not compare volatile fields that would force a write every request.

2. Add a periodic heartbeat

If the provider state has not changed, insert a heartbeat only when the most recent stored record is older than 15 minutes.

This ensures future uptime charts have continuity without writing every 30 seconds.

Expected behavior:

- state change: persist immediately
- unchanged state under 15 minutes old: skip insert
- unchanged state 15 minutes or older: persist heartbeat

Use a named constant for the heartbeat interval.

3. Keep tenant isolation

All latest-record lookups and inserts must be scoped by the authenticated Clerk user ID and provider.

Never compare or deduplicate across users.

4. Improve indexes

Replace or supplement the current indexes with indexes aligned to actual query patterns:

- (user_id, provider, checked_at DESC)
- (user_id, checked_at DESC)

Avoid unnecessary duplicate indexes if the new composite indexes fully cover existing queries.

Use the project's established raw-SQL bootstrap pattern.

Make index creation idempotent with IF NOT EXISTS.

5. Move pruning out of every write

Do not run the retention DELETE after every health snapshot.

Implement a low-cost pruning guard so cleanup runs no more than once per 24 hours per server process.

Requirements:

- use a module-level last-prune timestamp or an equivalent simple mechanism
- preserve the 90-day retention period
- run pruning asynchronously
- log failures safely
- do not block the health response
- do not create a new scheduled-job framework for this task

Use the checked_at index efficiently.

6. Strengthen secret sanitization

Update sanitizeDetail() to redact likely Meta/Facebook token formats, including common prefixes such as:

- EAA
- EAAB
- EAAC
- EAAG
- EAAM

Also ensure sanitization covers:

- Bearer tokens
- access_token
- refresh_token
- client_secret
- api_key
- authorization headers
- Google token formats already handled

Do not log the original secret value during testing.

7. Preserve allowlist metadata

Continue using allowlist-based safeMeta().

Review every allowed metadata field and confirm it cannot contain:

- tokens
- secrets
- authorization headers
- sensitive customer data

Do not switch to blocklist-only metadata filtering.

8. Add OpenAPI coverage

Update:

/lib/api-spec/openapi.yaml

Document:

GET /api/diagnostics/health-history

Query parameters:

- provider: optional string
- limit: optional integer, minimum 1, maximum 500

Response schemas should include the real returned fields, including:

- id
- provider
- status
- checkedAt
- lastSuccessAt
- errorMessage
- healthScore
- metadata

Use nullable fields where the backend can return null.

9. Regenerate generated clients and schemas

Run the project's existing code-generation workflow.

Regenerate:

- Zod schemas
- React API client types/hooks
- any other generated contract artifacts used by the project

10. Remove manually duplicated frontend types

Update SystemDiagnosticsPage.tsx to use generated response types or generated hooks where available.

Do not leave a hand-written HealthHistoryItem interface that duplicates the OpenAPI schema.

Continue using useApiFetch() for authenticated requests if the generated hook does not follow the established Clerk authentication requirement.

11. Validate query parameters more strictly

For limit:

- accept only finite positive integers
- clamp to maximum 500
- default to 100
- reject or safely normalize invalid values

Keep provider filtering parameterized.

12. Preserve fire-and-forget safety

Persistence and pruning failures must:

- be caught
- be logged with sanitized messages
- never produce unhandled promise rejections
- never crash the API process
- never delay the health response

13. Add focused tests

Add tests for:

- state change inserts immediately
- identical state under 15 minutes does not insert
- identical state after 15 minutes inserts a heartbeat
- different users do not deduplicate against each other
- provider filtering remains tenant-scoped
- limit is bounded at 500
- Meta/Facebook token strings are redacted
- Bearer/access/refresh token strings are redacted
- pruning guard runs at most once per 24 hours
- persistence failure is handled without an unhandled rejection

Use existing project testing conventions.

Do not make real provider API calls.

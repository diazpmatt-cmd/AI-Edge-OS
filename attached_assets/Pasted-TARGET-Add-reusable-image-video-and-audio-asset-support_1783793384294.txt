TARGET: Add reusable image, video, and audio asset support to the Publishing Center and Content Autopilot.

IMPORTANT

Follow the AI Edge audit-first workflow:

1. Audit
2. Consolidate
3. Verify
4. Expand

Current confirmed issue:

The Publishing Center upload UI only accepts:

- JPG
- PNG
- WEBP
- GIF

It rejects MP4 and MP3, even though the existing object-storage workflow can store arbitrary content types and the YouTube publisher already supports an attached MP4 through videoUrl.

The same reusable media capability must be available in Content Autopilot.

Do not:

- create a second storage system
- create a YouTube-only uploader
- store media binaries in PostgreSQL
- assume every platform accepts MP3 or MP4
- claim bare MP3 publishing is supported where the provider cannot publish audio-only posts
- bypass existing authentication
- modify unrelated mobile code

PHASE 2 — DEFINE ONE SHARED MEDIA-ASSET MODEL

Create or reuse one shared media model.

A media asset should support:

- id or objectPath
- originalFilename
- mediaKind:
  - image
  - video
  - audio
- mimeType
- extension
- byteSize
- width when known
- height when known
- durationSeconds when known
- aspectRatio when known
- storagePath
- uploadStatus
- validationStatus
- createdAt

Do not require every metadata field when the current server cannot inspect it.

Keep unknown metadata explicitly null rather than guessing.

Preserve backward compatibility with existing imageUrl and videoUrl records.

If a new audio field is required, prefer:

- audioUrl
or
- mediaAssetId

based on the existing architecture.

Update OpenAPI first if contracts change.

Update Zod schemas and generated clients where applicable.

PHASE 3 — CENTRALIZE FILE-TYPE RULES

Create one shared media validation configuration instead of separate page-level arrays.

Initial allowed types:

Images:
- image/jpeg
- image/png
- image/webp
- image/gif

Video:
- video/mp4

Audio:
- audio/mpeg
- audio/mp3 if encountered as a browser-reported alias

Allowed extensions:

- .jpg
- .jpeg
- .png
- .webp
- .gif
- .mp4
- .mp3

Validate using:

1. MIME type
2. file extension
3. nonzero byte size
4. configured maximum size

Do not trust filename alone.

Reject MIME/extension mismatches safely.

PHASE 4 — SIZE LIMITS

Audit current infrastructure and apply truthful limits.

Suggested initial pilot limits unless existing infrastructure supports safer values:

Images:
- maximum 10 MB

MP3:
- maximum 50 MB

MP4:
- maximum 100 MB for the current in-memory YouTube publishing flow

If object storage allows larger files but the API publisher loads the entire file into memory, enforce the smaller publishing-safe limit.

Display the actual limit in the UI.

Do not advertise the storage provider’s maximum as the safe application limit.

PHASE 7 — PLATFORM CAPABILITY RULES

Use the canonical provider registry and shared media compatibility logic.

For the current BB&B pilot:

FACEBOOK
- images: supported if existing publisher supports them
- MP4: supported only if the existing Meta video-post handler supports it
- MP3 alone: not directly publishable as a normal Facebook post unless an existing supported workflow proves otherwise

INSTAGRAM
- images: supported
- MP4: supported only if existing video/Reel publishing is implemented
- MP3 alone: not directly publishable

GOOGLE BUSINESS PROFILE
- images: supported
- MP4: do not claim support unless the existing GBP endpoint supports it
- MP3: not directly publishable
- while quota remains zero, status remains manual publish required

YOUTUBE
- MP4: supported and required for video upload
- image: thumbnail candidate only; custom thumbnail upload may still be unimplemented
- MP3 alone: not directly publishable as a YouTube video
- MP3 may be stored as narration/source audio for future video assembly

For deferred platforms, derive capability truthfully from the registry.

Do not let “upload accepted” imply “provider publish supported.”

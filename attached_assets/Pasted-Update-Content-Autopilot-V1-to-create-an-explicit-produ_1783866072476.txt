Update Content Autopilot V1 to create an explicit, production-safe publishing workflow.

The current interface does not clearly distinguish generating, queueing, scheduling, and actually sending content to external platforms. Fix that ambiguity.

Begin by auditing the current Content Autopilot page, button handlers, API routes, database tables, platform connectors, queue logic, scheduler logic, and publishing adapters. Before changing code, determine exactly what “Generate Next Week” and “Queue All Selected” currently do.

Do not assume content is being published. Trace every action from the UI through the backend and identify whether Facebook, Instagram, Google Business Profile, and YouTube have real authenticated publishing integrations or only placeholder/queue behavior.

## Required workflow

Implement these distinct states:

1. Draft
2. Generated
3. Awaiting approval
4. Approved
5. Queued
6. Scheduled
7. Publishing
8. Published
9. Published with warning
10. Failed
11. Cancelled

Do not use “Ready” as a substitute for “Published.”

## Explicit Send/Publish action

Add a clearly labeled primary action:

“Send / Publish Selected”

This button must be visually and functionally separate from:

- Generate Next Week
- Approve
- Queue All Selected
- Schedule

The Send / Publish button must not appear enabled unless:

- content has been generated;
- the post has been approved;
- at least one platform is selected;
- the selected platform has a valid active connection;
- required media and text validations pass;
- a scheduled time is valid, or the user selected “Publish now.”

Before publishing, show a confirmation dialog containing:

- number of content items;
- selected platforms;
- scheduled dates and times;
- whether the action is “Publish now” or “Schedule”;
- total expected platform publishing attempts;
- warnings for disconnected or unsupported platforms.

Confirmation text should explicitly say:

“You are about to send content to external platforms.”

Require a final Confirm Publish action.

## Platform delivery statuses

For every content item and every selected platform, show an independent delivery status.

Use these status colors:

- Gray: Draft / Not queued
- Blue: Queued or scheduled
- Yellow: Warning, delayed, pending confirmation, or partial success
- Green: Confirmed published successfully
- Red: Failed
- Purple: Awaiting approval
- Orange: Publishing in progress

A card may only turn green after the platform API returns a confirmed success response.

For every successful publication, store and display:

- platform name;
- publication timestamp;
- external post ID;
- external post URL when available;
- API response status;
- publishing attempt number;
- actor who approved/sent it.

For failures, display:

- safe error summary;
- failure timestamp;
- whether retry is allowed;
- Retry button;
- View details button with sanitized diagnostics.

Never expose access tokens, authorization headers, cookies, or raw credentials.

## Publish summary panel

Add a summary panel above the platform cards:

- Total selected

- Publishing
- Warning
- Failed

“3 of 4 platforms published successfully. Google Business Profile failed and requires attention.”

Do not report “sent” if the item is only queued or scheduled.

## Three-posts-per-day schedule

Support up to three content slots per day:

- Morning
- Afternoon
- Evening

Default suggested times should be configurable. Start with:

- Morning: 8:00 AM
- Afternoon: 1:00 PM
- Evening: 7:00 PM

Use the client’s configured IANA timezone. For Bed Bugs & Beyond, use the canonical business timezone already configured in client context rather than hardcoding browser time.

The weekly planner should support:

- 1 post per day
- 2 posts per day
- 3 posts per day

When 3 posts per day is selected, generate up to 21 weekly content slots.

Each content slot should be one campaign item that may be adapted to each selected platform. Do not generate three completely unrelated posts per platform unless explicitly configured.

For example:

Monday Morning:
- Facebook adaptation
- Instagram adaptation
- Google Business Profile adaptation
- YouTube adaptation, only when the content format is valid for YouTube

Monday Afternoon:
- separate campaign item with platform adaptations

Monday Evening:
- separate campaign item with platform adaptations

## Platform-specific safeguards

Do not assume all content can be published to every platform.

Facebook and Instagram:
- validate connected Meta account/page;
- verify required image/video format;
- store returned post/media IDs.

Google Business Profile:
- verify that the Google Business Profile publishing connector is actually implemented and authenticated;
- if not implemented or unsupported, show “Not connected” or “Publishing unavailable”;
- never show green “Ready” merely because text was generated.

YouTube:
- distinguish between:
  - YouTube video upload;
  - YouTube Shorts upload;
  - metadata/description generation only.
- Text alone must not be represented as a publishable YouTube post.
- Require a valid video file before enabling YouTube publishing.
- If only metadata is generated, label it “Metadata ready — video required.”

## Queue versus schedule versus send

Define these actions precisely:

- Generate: creates platform-specific drafts only.
- Approve: authorizes the content for later scheduling or publishing.
- Queue: places approved content into the internal publishing queue.
- Schedule: assigns an intended future publication time.
- Send / Publish: invokes the real platform publishing adapter immediately.
- Scheduled publication worker: invokes the real adapter at the scheduled time.
- Published: confirmed external platform success only.

Update all labels, help text, tooltips, and status messages to follow these definitions.

## Publishing architecture

Create or reuse a canonical publishing service.

Suggested sequence:

1. Resolve client and ownership.
2. Validate approval.
3. Validate platform connection.
4. Validate content and media requirements.
5. Create deterministic publishing attempt ID.
6. Enforce idempotency.
7. Mark attempt as publishing.
8. Call the correct platform adapter.
9. Save external post ID and URL.
10. Mark published, warning, or failed.
11. Record audit event.
12. Return sanitized platform-specific result.

Do not call external platforms directly from React components.

Use backend routes and provider adapters.

Prevent duplicate posting if the user presses Send twice or refreshes the page.

## Approval safety

Keep the existing pilot rule:

- every generated post requires explicit approval;
- no autonomous publishing;
- queueing does not equal approval;
- scheduling does not bypass approval;
- Send / Publish must reject unapproved content.

Do not modify Bed Bugs & Beyond service safety rules:

- termites remain coming soon;
- wildlife removal remains not offered;
- whole-home bed bug heat treatment remains not offered;
- fumigation remains active;
- approval-required mode remains enabled.
